# 交易所接入问题复盘与工程规范

本文基于 Atlas Ledger 从 Binance、OKX、Bitget、Bybit、Hyperliquid 和 Polymarket
接入到生产运行期间出现过的真实问题、用户反馈、修复代码和 Git 提交记录整理。目标不是
重复 API 文档，而是说明交易所账户、当前仓位、平仓历史和账务查询最容易出错的地方，
以及新增交易所时必须遵守的实现与验收规范。

## 1. 先明确系统边界

Atlas Ledger 是公开只读聚合平台。当前代码只允许查询，不提供下单、撤单、主动平仓、
划转、提币或调整杠杆功能。这里的“平仓接入”是指读取用户在交易所完成的平仓结果，
不是由平台发送平仓指令。

这个边界必须长期保持：

- 中心化交易所只接受纯只读 API Key，连接时主动检查权限。
- Hyperliquid 和 Polymarket 只使用公开地址，不接收私钥、助记词或签名密钥。
- 适配器只包含读取接口；安全检查会拦截交易、划转和提币调用。
- 错误日志、API 响应和巡检消息不得出现 Secret、Passphrase、签名原文或上游敏感响应。

如果未来单独开发交易系统，必须使用独立服务、独立凭证、独立数据库权限和独立审计链，
不能在只读适配器中顺手增加下单接口。订单写操作还必须额外解决客户端订单号幂等、超时后
查单而非盲目重试、部分成交状态机、撤单竞态、WebSocket 断线补偿和成交对账；这些能力
不属于当前项目。

## 2. 最重要的结论

1. **交易所字段名相同，不代表单位相同。** `pos`、`size` 可能是币数、张数、USD
   名义价值或反向合约面值，不能默认“一张等于一个币”。
2. **成交、订单、仓位周期是三种不同粒度。** 一个订单可拆成多笔成交；一次仓位可分批
   减仓；同一个交易所 `positionId` 甚至可能在归零后复用。
3. **稳定幂等键不能包含会变化的更新时间。** 否则每次部分平仓都会被写成一笔新交易。
4. **历史接口不是天然完整。** 需要处理分页、时间窗口上限、数据保留期、最终一致性和
   API Key 权限差异，并明确标记 `COMPLETE`、`PARTIAL` 或 `UNSUPPORTED`。
5. **已实现毛收益、资金费、手续费、净收益必须分开保存。** 页面公式统一不能替代事实
   明细，正负号也不能靠字段名称猜测。
6. **当前仓位消失是高价值事件。** 只按固定周期拉平仓历史会让用户长时间看不到结果，
   应在检测到全部或部分减仓时立即补拉。
7. **数据库旧错数据需要迁移或清理脚本。** 修复适配器只会保证未来正确，不会自动修复
   已经重复、覆盖或错误标记的历史记录。
8. **不能用测试账户的成功代表所有产品线。** USDT、USDC、反向、统一账户、组合保证金、
   Hedge/One-way、TradFi、HIP-3 和预测市场组合单都可能走不同接口或使用不同语义。

## 3. 当前仓位查询踩过的坑

### 3.1 合约张数不等于标的币数

生产环境曾出现 OKX HYPE 仓位保证金错误：接口的 `pos` 是合约张数，而
`1 张 = 10 HYPE`。如果直接使用 `开仓价 × pos`，仓位价值、保证金、收益率都会成倍错误。

最终做法是：

- 优先相信交易所返回的 USD 名义价值，例如 OKX `notionalUsd`。
- 标的数量用 `abs(notionalUsd) / markPrice` 推导，而不是直接使用合约张数。
- 开仓名义价值使用 `当前名义价值 × entryPrice / markPrice` 回推。
- 保证金统一使用 `开仓名义价值 / leverage`，缺少杠杆时才回退交易所报告值。
- 这套公式放在共享的 `position_math` 服务中，不为单个交易所复制一套临时逻辑。

相关修复：`2a1f457`、`a1a2a02`。

### 3.2 同一个交易所的接口版本字段也会不同

Binance `positionRisk` V3 曾导致 GOOGL 合约显示 `0x / UNKNOWN`，因为该版本响应没有项目
需要的杠杆和保证金模式字段；V2 反而是这些字段的可靠来源。经验是不能因为版本号更新就
默认新版本字段更完整，必须用真实账户响应逐字段验收。

相关修复：`66e0086`。

### 3.3 非主市场不能只查默认账户状态

Hyperliquid 的 CXMT 属于 HIP-3 DEX。只请求默认 `clearinghouseState` 会完全漏掉仓位，
错误的资产索引解析还会把它显示成 `XYZ-USDT-PERP`。正确实现需要：

- 先调用 `perpDexs` 枚举默认及 HIP-3 DEX。
- 分别查询各 DEX 的 `clearinghouseState`。
- 保留原始 `dex:coin` 身份用于数据源定位，展示标准化时只处理正确的 coin 部分。
- 账户汇总和仓位查询共享同一批异步请求，避免重复调用上游。
- 统一账户不能把现货权益和每个 DEX 的账户价值重复相加。

相关修复：`2005d89`、`3b645d4`。

### 3.4 未实现盈亏有“当前值”和“统计期变化”两种口径

用户在接入 API Key 前已经持仓且亏损 20 USDT，平台若只展示“接入后的变化”，就可能显示
0.1 USDT，虽然计算本身没有错，但完全不符合“当前仓位收益”的用户理解。当前仓位主值应
始终显示交易所当前完整未实现盈亏；统计期基线只能用于内部对账，不能冒充当前盈亏。

相关修复：`2feea69`、`96efe97`。

### 3.5 收益率必须基于本金，而不是裸价格变化

杠杆仓位不能只显示 `(标记价 - 开仓价) / 开仓价`。当前仓位收益率应为：

```text
当前仓位收益率 = 当前未实现盈亏 / 仓位本金 × 100%
仓位本金 ≈ 开仓名义价值 / 杠杆倍数
```

只有在交易所无法提供可靠杠杆或本金时，才降级展示按多空方向计算的价格变化，并明确说明
这是价格变化而不是杠杆收益率，不能用猜测的杠杆补齐。

相关修复：`d1f6c11`、`0d12e74`、`1fd7cfb`、`3233e4e`。

## 4. 平仓历史踩过的坑

### 4.1 不能把时间戳直接当仓位身份

最严重的一类错误是把 `updatedTime`、`uTime` 或本次同步时间放进 `source_record_id`。
部分平仓时这些时间会变化，于是同一仓位被写成多笔，累计收益也被重复计算。

幂等键必须描述“业务实体”，而不是“这次看到它的时间”。当前采用的主要策略：

| 平台 | 稳定身份策略 |
|---|---|
| Binance | 合并订单成交分片后，以完整开平仓周期及最终成交身份重建 |
| OKX | `instType + posId + cTime`，其中 `cTime` 区分被复用的 `posId` |
| Bitget | `productType + positionId`，同 ID 只保留最新累计状态 |
| Bybit | `category + close orderId` |
| Hyperliquid | 标的、方向和关闭成交身份重建周期 |
| Polymarket | outcome token `asset`；组合单使用官方组合身份 |

### 4.2 OKX 部分平仓返回的是累计状态

KIOXIA 分两次平仓时，网站曾显示两笔且金额重复，而 OKX App 只有一笔。原因是
`positions-history` 在同一周期分批减仓时保持 `posId`、`cTime` 不变，但更新 `uTime`、
累计数量、均价和盈亏。正确逻辑是更新同一行，而不是累加两行。

随后又发现只用 `posId` 也不够：仓位归零后再次开仓，OKX 可能复用 `posId`。因此最终
必须加上代表独立开仓周期的 `cTime`。SPCX、SNDK 等缺失记录也说明增量同步不能只相信
最新一页或单一关闭时间边界，需要保留重叠窗口并提供周期重建工具。

相关修复：`721be22`、`2be6f4d`。

### 4.3 Binance 没有可直接照搬的“历史仓位”接口

Binance 历史仓位由 `userTrades` 成交重建。这里至少有四个坑：

- 一张订单可返回多笔 fill，必须先按订单合并，数量和费用求和，价格按数量加权。
- Hedge Mode 与 One-way Mode 的方向和开平判断不同。
- 部分平仓不能提前结束周期；反手交易需要先关闭旧方向再建立新方向。
- 数据来自交易所成交，虽然仓位周期是本地重建，也不应笼统标成“本地猜测”；当前标记为
  `EXCHANGE_FILLS_RECONSTRUCTED`。

相关修复：`44acff4`、`01a92e9`、`0aa28c2`。

### 4.4 Bitget 也会重复返回阶段状态

Bitget 历史接口可能对同一个 `positionId` 返回不同阶段状态。若来源 ID 拼接关闭时间，
就会产生碎片。应按 `productType + positionId` 归并，并以 `utime` 选择最终累计记录；
老数据需要单独运行清理脚本迁移到新身份。

相关修复：`01a92e9`。

### 4.5 Hyperliquid 历史仓位需要从 fills 重建

Hyperliquid 的当前状态接口不能直接给出完整仓位周期，历史需要根据 `userFillsByTime`
重建。需要正确处理部分减仓、反手、费用、方向、分页和 HIP-3 标的；不能把“由交易所成交
重建”误标为完全不可验证的本地记录。同步失败时还必须回滚当前事务后再写安全错误，否则
数据库事务进入失败状态，连失败记录本身也保存不下来。

相关修复：`44acff4`、`2005d89`、`8211330`。

### 4.6 Polymarket 的身份、翻译和组合单有独立语义

Polymarket 普通仓位的响应时间戳可能变化，不能用时间戳去重，应使用 outcome token。
当前仓位转入历史仓位后也不应重新翻译：原文与简体中文译文按 outcome token 持久化缓存，
当前和历史共用。组合单不能按普通单逐腿相加，需要调用组合接口，开放仓位按子市场概率
估值，结算后使用官方结算金额、成本和费用重建收益。

官方已平仓数据缺少可靠原始开仓时间，因此必须标记为 `PARTIAL`，不能伪造 `COMPLETE`。

相关修复：`4764e05`、`653dd73`。

## 5. 收益、资金费和手续费踩过的坑

### 5.1 页面口径不统一会让正确数字看起来也像错误

项目曾同时出现“累计收益”“已实现收益”“已实现毛收益”“净收益”“统计期变化”等名称，
但底层来源并不一致，最终导致毛收益减费用无法对上净收益。现在必须先定义事实，再定义
展示公式：

```text
历史仓位净收益 = 已实现毛收益 + 归属该仓位的资金费 - 归属该仓位的手续费
交易净收益 = 已实现收益流水 + 资金费流水 - 手续费流水
权益口径收益 = 当前权益 - 统计期初权益 - 净充值提现
当前持仓收益 = 当前仓位未实现盈亏之和
```

不同接口对手续费和资金费的正负号约定不同；适配器必须在归一化层统一符号，页面不能再次
猜测或反转。Bybit `closedPnl` 已经包含费用，拆分明细则以 Transaction Log 为准；如果再
从净收益重复扣费，会二次计算。

### 5.2 仓位表与账务流水不能互相替代

历史仓位适合展示每笔交易，但账务接口才是资金费、手续费、充值提现和账户级收益的权威
来源。一次资金费可能跨越多个持仓时点，也可能没有可靠的单仓归属；因此事实表必须分别
保存，汇总表只作为可重建读取模型，不能成为唯一账本。

### 5.3 非稳定币流水不能无汇率冒充 USD

对于非 USD、USDT、USDC 结算的历史费用或收益，如果没有该时刻的可靠美元价格，不能
直接把币数量当美元金额。正确行为是保留可验证字段并将完整性降为 `PARTIAL`。

相关修复集中在 `35e8627` 以及后续收益口径提交 `0f6a7d8`、`7998014`、`99534c2`、
`ae264ca`、`fa72a6a`。

## 6. 同步、分页和最终一致性踩过的坑

### 6.1 固定 10 分钟同步让平仓看起来像丢失

历史仓位最初每 600 秒同步，网页又每 60 秒刷新，极端情况下平仓后约 11 分钟才显示。
这不是查询接口慢，而是调度策略不符合用户预期。当前策略为：

- 当前仓位每 15 秒同步。
- 已平仓仓位每 60 秒兜底同步。
- 检测到同一标的和方向的持仓数量减少或消失时，立即补拉历史仓位。
- 网页每 60 秒刷新；交易所自身仍可能有数十秒的最终一致性延迟。
- 仓位未变化时不额外请求平仓接口，避免无意义消耗限频额度。

相关修复：`2add096`。

### 6.2 所有历史接口都要同时处理时间分片和游标分页

只做其中一个不够。典型限制包括：Bybit 单次最多 7 天、Bitget 单次最多 30 天且总保留
约 90 天、OKX 归档账单约 3 个月。标准实现必须：

1. 按官方允许的最大时间窗口切片。
2. 每个时间片继续使用 cursor / page 分页直到结束。
3. 按稳定来源 ID 幂等写入。
4. 上次成功游标回退 5 分钟形成重叠窗口，吸收上游延迟。
5. 对仍持有的长期仓位，将平仓查询起点扩展到已知开仓时间。
6. 只有整个请求链完整成功后才推进游标；失败时保留旧游标以便下次补拉。

### 6.3 网络成功不代表业务成功

HTTP 200 仍可能包含交易所业务错误码；HTTP 超时也不代表请求一定没有在上游执行。只读
请求可以做有限指数退避重试，但错误信息必须脱敏。Bybit 还存在区域 IP 限制，服务器出口
必须先验证；API Key 的账户类型、产品权限和 IP 白名单也要在真实生产网络中测试。

### 6.4 并发不能破坏事务边界

余额、当前仓位、平仓和账务流可以并发请求，但每个账户只能有一个同步锁。某个可选账务流
失败时，可以保存资产与当前仓位并把完整性降级；数据库写入失败时必须整体回滚，再在新的
可用事务中写入脱敏错误。不同账户之间应故障隔离，不能因为一个账户失败阻塞全部账户。

## 7. 数据库与接口设计经验

### 7.1 事实表、最新状态表、读取模型要分层

- 当前余额和当前仓位是“最新状态”，适合覆盖写入专用表。
- 历史仓位、成交、资金费、手续费和现金流是“事实”，必须幂等追加或更新。
- 收益分析、风险、对账和同步状态是“读取模型”，可在同步后增量刷新并每日全量校准。
- 读取模型必须能从事实表重建，缺失或过期时接口应回退计算，不能返回永久陈旧缓存。

这避免了每次打开网页都扫描全部历史，也避免把缓存误当不可恢复的账本。

### 7.2 修复代码后必须处理生产旧数据

去重键、周期划分或费用口径改变后，应提供具有以下特性的维护工具：

- 默认 preview / dry-run，输出将合并、删除、更新的数量。
- 按交易所和账户限定范围，不做全库模糊删除。
- 执行前备份数据库并验证备份可恢复。
- 在一个事务内修改事实行并重建相关日汇总、收益读取模型和完整性状态。
- 重复运行结果一致，旧格式来源 ID 能迁移到新格式。

项目已经为 OKX 部分平仓、OKX 周期重建、Binance fill 碎片和 Bitget 历史碎片提供过这类
脚本。经验表明“以后同步正确”不等于“生产数据已经正确”。

### 7.3 时间统一存 UTC，业务日明确用北京时间

交易所时间戳统一转换为带时区 UTC 存储；页面再本地化。日收益和每日快照使用
`Asia/Shanghai` 自然日，不能混用 UTC 00:00，否则凌晨数据会落到错误日期。开仓时间、
平仓时间、上游更新时间和本次采集时间必须是四个不同概念，不能互相替代。

## 8. 新交易所接入标准流程

### 8.1 接入前调研

- 确认现货、线性合约、反向合约、期权、统一账户和子账户的覆盖范围。
- 列出账户权益、余额、当前仓位、历史仓位、成交、账单和权限检查接口。
- 记录签名原文、参数排序、时间偏差、recvWindow、分页和时间范围限制。
- 确认每个金额字段的币种、正负号、是否已含费用，确认 size 的真实单位及合约乘数。
- 确认历史保留期、上游最终一致性延迟、区域 IP 限制和 API Key 权限要求。
- 收集至少一组真实但脱敏的响应，覆盖多/空、部分平仓、反手、USDT/USDC、Hedge/One-way。

### 8.2 适配器输出契约

所有适配器必须输出同一语义，而不是把原始字段直接交给前端：

- 账户：总权益、可用余额、已用保证金、未实现盈亏、未估值资产数。
- 当前仓位：稳定来源 ID、标准化标的、方向、标的数量、USD 仓位价值、开仓/标记价、
  杠杆、保证金模式、本金、未实现盈亏和开仓时间。
- 历史仓位：独立周期 ID、方向、开平时间与均价、最大仓位、毛收益、资金费、手续费、
  净收益、本金、收益率、数据来源和完整性。
- 账务流：已实现收益、资金费、手续费、充值提现分别返回，每条都有稳定来源 ID、时间、
  币种、USD 金额和可选标的。

缺失数据使用 `None` 和完整性标记，禁止填入看似合理的假值。

### 8.3 必测场景

每个新交易所至少要自动化验证：

- 签名固定向量和参数编码。
- 纯只读权限通过，交易、划转或提现权限存在时拒绝连接。
- 空账户、仅现货、仅合约、多个结算币种。
- 多仓、空仓、Hedge Mode、One-way Mode。
- 合约乘数不为 1、反向合约、缺失杠杆、逐仓与全仓。
- 一张订单多 fill、部分平仓、多次部分平仓、完全平仓、反手、同 ID 再开仓。
- 分页边界、恰好满页、跨最大时间窗口、重叠窗口重复数据。
- 资金费和手续费正负号、净收益恒等式、非稳定币结算。
- 上游超时、业务错误码、权限不足、单个账务流失败和数据库写入失败。
- 重复同步不新增重复事实行；旧游标不因失败前移。
- 前端筛选、分页、移动端展示、数据来源和完整性提示。

项目级契约测试还必须保证所有注册适配器都真正实现 `get_closed_positions`，声明支持的每个
账务流都有具体实现，防止再次出现“接口存在但函数只是空实现”的情况。

### 8.4 上线步骤

1. 本地运行交易所专项测试、后端全量测试、前端测试、Lint 和安全扫描。
2. 提交前检查差异，确认没有 `.env`、真实 API Key、数据库密码或响应样本中的隐私数据。
3. 推送 Git 后，在生产服务器先验证目标交易所公网 API 可访问。
4. 创建并恢复验证 PostgreSQL 备份；记录迁移版本和关键表数量。
5. 构建镜像、执行幂等迁移、滚动更新 backend；必要时重建 gateway 避免旧容器 DNS。
6. 验证容器健康、公共 API、最近同步任务、错误日志和目标账户数据完整性。
7. 若改变去重或计算逻辑，先 dry-run 生产修复工具，再执行并复核汇总恒等式。

## 10. 最终检查清单

新增或修改交易所适配器，在宣布完成前必须能回答“是”：

- [ ] 项目仍然没有任何交易、划转或提币写调用。
- [ ] 使用纯只读权限或公开地址，并验证了真实生产网络。
- [ ] size、contract value、notional、margin 和 PnL 单位已经逐字段确认。
- [ ] 当前仓位显示完整未实现盈亏，而不是仅显示接入后的变化。
- [ ] 部分平仓更新同一周期，再开仓不会覆盖旧周期。
- [ ] 一张订单的多个 fill 不会形成重复历史仓位。
- [ ] 毛收益、资金费、手续费、净收益及其正负号可以互相对账。
- [ ] 时间切片、游标分页、重叠窗口和历史保留期全部处理。
- [ ] 上游延迟、失败和权限不足不会推进成功游标或污染其他账户。
- [ ] 数据来源与完整性如实展示，不用猜测值伪装完整。
- [ ] 修复逻辑配有生产旧数据的 preview、清理或重建方案。
- [ ] 单元、适配器契约、数据库幂等、前端和安全检查全部通过。
- [ ] 上线前备份经过恢复验证，上线后检查同步任务与错误日志。

只要其中任意一项不能确认，接入就还没有真正完成。
